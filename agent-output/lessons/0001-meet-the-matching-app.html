Meet the matching app

Today's win: the project runs on your machine and you can trace the whole mentor decision flow with your own clicks.

Before we chase the bug Ops reported, you need the app alive in front of you. Step 1 of the exercise is run the project locally — so let's do that now, together with a guided walk of what you're seeing. Full details live in the architecture map.

The shape of the app

A student (MentorRequest) is proposed to a mentor (StudentProposal). The mentor gets an email with two links: accept, decline. Each link carries the proposal's UUID — a capability token: no login, just possession of the link. Clicking a link records the decision in a response JSON blob, then a follow-up form records a match_rating (accept) or decline reason (reject).

Run it

Your machine has node and npm, but uv is missing. Install it first:

curl -LsSf https://astral.sh/uv/install.sh | sh

Then restart your shell (or source ~/.bashrc / ~/.zshrc) and bring up the backend:

cd backend
uv sync
uv run python manage.py migrate
uv run python manage.py seed_proposal
uv run python manage.py runserver

Expected: seed_proposal prints a UUID plus accept and decline links. In a second terminal:

cd frontend
npm install
npm run dev

Open http://localhost:5173/ — that's the dev inbox.

Walk the happy path

  1. Inbox. You should see "Student proposal: Jamie Student" with two links. This is an OutboxMessage, a stand-in for real email.
  2. Click Accept. The page auto-fires a POST — no button press. You get "Your response has been recorded" plus a 0–10 rating dropdown.
  3. Pick a rating, submit. This is a PATCH to the same endpoint.
  4. Inspect. Open /proposals and read the raw response JSON. You should see value: "accept", match_rating, and recorded_at in one dict.
  5. Repeat the reject path. Re-seed (uv run python manage.py seed_proposal), click Decline, fill the reason form, and inspect the JSON again.

Check yourself

Before moving on, retrieve from memory — no scrolling up.

Which model stores the mentor's decision?

Each proposal sent to a mentor carries the decision in its response JSON.

Which HTTP method records the accept or reject decision itself?

POST sets value and recorded_at; PATCH only adds reason or match_rating afterwards.

Which HTTP method records the decline reason?

The feedback form PATCHes reason or match_rating onto the same response record.
