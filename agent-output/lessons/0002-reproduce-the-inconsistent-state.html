Reproduce the inconsistent state

Today's win: you can produce the exact state Ops reported, on demand — and describe it precisely in terms of the response JSON.

Ops said: proposals that look accepted but contain decline reasons. In an interview, "reproduce" means more than "I saw it once" — it means you can trigger it deliberately and say exactly what changed. Both servers should still be running from last lesson. Full flow details live in the architecture map.

Translate the report into data

Before touching anything, translate the Ops report into a data statement. You inspected raw response JSON at /proposals last lesson.

Notebook first: what would "accepted proposal with decline reasons" look like as that JSON dict? Write the object out, keys and all, before scrolling further.

Something like this — the exact reason keys don't matter:

{
  "value": "accept",          ← looks accepted
  "recorded_at": "...",
  "reason": { ... }           ← ...but carries decline answers
}

Hold that picture. Your repro succeeds only if you see exactly this combination.

Plan the repro before you click

In lesson 1 each path was clean: accept = POST then PATCH match_rating; decline = POST then PATCH reason. Both paths write into one shared dict. Ops's state mixes a piece of one path with a piece of the other. So ask:

  1. Re-read the endpoints table row by row. What does POST refuse to do twice? What does PATCH refuse to do twice — and, crucially, what does it never ask about?
  2. A mentor clicks Accept. Then they reopen the email and click Decline. On mount, ReviewStudent.jsx fires a GET and a POST in parallel — what does the server answer to that second POST, and what does the frontend do with that answer? (The map's frontend tour has the sentence you need.)
  3. After that, the decline feedback form renders. When the mentor submits it, which request carries the checked reasons, and which dict does it merge into?

Notebook: write your predicted click sequence and the predicted final JSON. A repro you can't predict is a repro you can't defend in an interview.

Run it

  1. Get a fresh proposal: uv run python manage.py seed_proposal (backend terminal).
  2. Execute your predicted sequence in the dev inbox at localhost:5173.
  3. Watch the network tab while you go. Note each request's method and status — one of them will not be a 2xx, yet the page will act as if nothing happened.
  4. Open /proposals and compare the raw JSON against your prediction. Success = value: "accept" and a populated reason.
  5. Run it a second time from scratch. A good repro works every time, not once.
Stuck after five minutes? Open me.

One more experiment

Now run the mirror image: from a fresh proposal, Decline — and stop there, do not submit the reason form. Then click Accept from the same email and submit a rating. Before clicking, predict request by request: which succeed, which are refused, and by which guard? The result is a different mixed state than Ops reported. Write down what you see.

Variant: repeat it, but submit the decline reasons before switching links. The outcome now diverges — which guard produces the difference? Both observations will earn their keep next lesson.

Check yourself

Before moving on, retrieve from memory — no scrolling up.

In Ops's inconsistent state, what does the response dict contain?

One dict, two paths' data mixed: the decision from one request, the decline answers from another.

During the repro, which request does the server refuse — and what does the frontend do about it?

"Response already recorded" is rendered as if the decision went through, so the flow continues to the feedback form.

Per the endpoints table, what does the PATCH guard check — and not check?

The guard only prevents a second PATCH — the decision stored in value is invisible to it.

Where do you verify the final on-disk state of a proposal?

The inbox shows fake emails; /proposals shows the raw response JSON that Ops was reading.

In the mirror experiment (decline decision, then accept link + rating), what did the second POST do to the recorded decision?

The replace in update_response only ever runs for a first decision — with value already present, the view blocks the POST before the service is called.
