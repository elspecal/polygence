Audit the existing suite first

Before writing anything new, hold every existing test in matching/tests/ against your criterion, assertion by assertion. One of them asserts that a mixed state — the very kind your criterion forbids — is the correct outcome. Find it.

Notebook: which test, which assertions, and what it should assert after the fix? This is a headline for your write-up: the suite didn't just miss the bug, it blessed it — evidence the decision↔follow-up rule was never specified.

Write the tests, watch them fail

  1. New file or new class — follow the house pattern in test_review_student.py: APIClient in setUp, seed Mentor/MentorRequest/StudentProposal, f-string URLs, format="json". To arrange a decided proposal, the house tests call StudentProposalService.update_response directly — do the same.
  2. Run uv run python manage.py test matching. Expect red.
  3. Verify each failure is red for the right reason: 400 != 200-style assertion mismatches, not setUp errors or typos. A red test that fails for the wrong reason tests nothing.

Design the guard

You already designed it in your notebook — now make the decisions explicit:

  1. Where does the check live — view or service? Re-read views.py:27-28 and views.py:37-38: where do all the other guards live, and where does mutation happen? Follow the house pattern.
  2. What does it refuse? Your criterion, verbatim: a reason only ever lands on value: "reject", a match_rating only on value: "accept" — and neither without a decision. What status and error shape? Match the existing errors.
  3. When is a reason "present"? The trap: if your guard treats any reason key as a reason, one of your happy-path rows will go red — the one sending the frontend's real body. Check what the service already does with falsy values (services/student_proposal.py:35) and make the guard agree with it. Your test suite, not this lesson, should be what catches this if you get it wrong — that's why that row exists.
  4. Order: before or after the existing reason-presence check? Does the observable outcome differ? Decide, one sentence in the notebook.

Implement, run, verify

  1. Add the guard, fitting the file's existing style. Smallest change that satisfies the criterion — you're submitting a fix, not a refactor.
  2. uv run python manage.py test matching — green, including the existing test you revised in the audit.
  3. Manual close-out: both servers up, rerun the lesson-0002 Ops repro click-for-click. Watch the network tab — which request dies now, and what does the mentor see? Confirm /proposals shows a dict your criterion allows.
  4. Rerun your mirror experiment too. Both repro recipes from your notebook should now be dead.
